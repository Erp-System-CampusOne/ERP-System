### Executive Summary

Work Package P2.9 modernizes authentication, session management, and authorization across CampusOne ERP without disrupting active users or breaking legacy frontend contracts.

All four mandatory architectural decisions from the P2.8/P2.9 readiness review were resolved before code modification:
1. **Decision A (JWT & Session Binding):** Redundant raw session secrets (`sec`) were removed from the bearer JWT. Server-side session identity is established strictly via signed `sid` claims backed by cryptographically hashed session tokens in `auth_sessions`.
2. **Decision B (Legacy-Token Cutoff):** An explicit server-enforced timestamp cutoff (`TRANSITION_CUTOFF_TIMESTAMP = 1791657000`) strictly rejects newly forged tokens lacking `sid`, while allowing legitimate legacy sessions to survive within a defined grace window.
3. **Decision C (Authorization Freshness):** RBAC authorization resolves against live `user_role_assignments` on every privileged request. Stale tokens retaining revoked administrative roles are denied access immediately (HTTP 403), eliminating token-bound privilege escalation.
4. **Decision D (Credential & Lockout Concurrency):** Failed login accounting and 15-minute lockouts use atomic database operations, preventing brute-force race bypass. Lazy credential backfill uses atomic upserts with safe concurrency handling, and password changes synchronize across legacy `User.password` and canonical `user_credentials.password_hash` in an explicit Prisma transaction.

The entire suite of **84 automated assertions passed with 100% success (0 defects)** in an isolated disposable PostgreSQL 17 environment.

### 2. Resolved Architectural Decisions

#### Decision A: JWT and Session Binding (No `sec` Claim)
- **Problem:** Embedding a raw session secret inside a signed bearer JWT provides no additional protection against token theft, as anyone possessing the bearer token also possesses the secret claim.
- **Resolution:** 
  - JWT claims include `id`, legacy `role`, canonical `roles`, canonical session ID `sid` (UUID), and token schema version `ver: 1`.
  - Raw session secrets are never placed in the JWT.
  - Server stores `session_token_hash` as a 64-character SHA-256 hex digest in `auth_sessions`.
  - Verification relies on the cryptographic signature of the JWT, expiry (`exp`), and active validation of the session record (`is_active = true`, `expires_at > now`).

#### Decision B: Legacy Token Transition Cutoff
- **Problem:** Allowing tokens without `sid` during a transition period creates a loophole if newly issued tokens can omit `sid` indefinitely.
- **Resolution:**
  - Defined `TRANSITION_CUTOFF_TIMESTAMP` (Unix epoch timestamp of cutover deployment).
  - Any JWT without `sid` whose `iat` (issued-at) is greater than or equal to the cutoff is rejected with `HTTP 401 Unauthorized`.
  - Eligible legacy tokens issued before the cutoff remain accepted during the transition grace period, but are blocked with `HTTP 403 Forbidden` if the user account is locked.

#### Decision C: Authorization Freshness & Stale Role Prevention
- **Problem:** If role authorization relies solely on JWT claims, a user whose role was revoked by an administrator retains elevated access until token expiration.
- **Resolution:**
  - `authorizeRoles(...)` middleware no longer trusts the `role` or `roles` array inside the JWT header.
  - For each protected request, `roleService.checkUserHasRole(userId, allowedRoles)` checks live active assignments in `user_role_assignments` where `is_active = true` and `valid_from <= now < valid_to`.
  - Revoking a role in PostgreSQL terminates privileged access immediately on the very next request.

#### Decision D: Credential & Lockout Concurrency
- **Problem:** Simultaneous failed logins can race, leading to lost increments and bypassing the 5-attempt brute-force lockout threshold.
- **Resolution:**
  - Failed login attempts are incremented atomically using Prisma's native atomic `{ increment: 1 }` operation (translating to PostgreSQL `SET failed_login_attempts = failed_login_attempts + 1`).
  - Account lockout is triggered when the updated count reaches `MAX_FAILED_ATTEMPTS = 5`, setting `locked_until = now + 15 minutes`.
  - Lazy credential backfill uses `upsert` with safe conflict handling so concurrent logins cannot fail or duplicate records.
  - Password updates use dual-write synchronization inside an explicit `$transaction` updating both `User.password` and `user_credentials.password_hash`.

### 3. Authentication Flow: Before vs. After P2.9

```
BEFORE P2.9 (Stateless & Coupled):
Client Request
      │
      ▼
authController.loginUser
      │──> Find user in User table
      │──> bcrypt.compare(password, User.password)
      │──> jwt.sign({ id, role })
      └──> Return { token, user }
(No session tracking; no server-side revocation; no multi-role resolution; no brute-force lockout)


AFTER P2.9 (Modernized & Authoritative):
Client Request
      │
      ▼
authController.loginUser
      │──> credentialService.verifyCredentials(identifier, password)
      │       ├── Check user_credentials (canonical)
      │       │     └── Check locked_until > now (403 if locked)
      │       │     └── bcrypt.compare(password, password_hash)
      │       │           ├── Match: Reset failed_login_attempts to 0
      │       │           └── Fail: Atomic increment attempts; lock if >= 5
      │       └── Fallback: Check User.password (legacy)
      │             └── Match: Atomic lazy backfill into user_credentials
      │
      │──> sessionService.createSession(userId, { ip, userAgent })
      │       └── Inserts auth_sessions record (SHA-256 token hash, 24h expiry)
      │
      │──> roleService.getUserActiveRoles(userId)
      │       └── Queries user_role_assignments (with legacy backfill fallback)
      │
      │──> jwt.sign({ id, role, roles, sid, ver: 1 })
      └──> Return { token, user: { ...user, roles } } [Exact frontend contract preserved]
```

### 5. HTTP Status Code Conventions

| Condition | HTTP Status | Response Payload | Semantics |
| :--- | :--- | :--- | :--- |
| Missing Authorization header | `401 Unauthorized` | `{ success: false, message: 'Access token required' }` | Unauthenticated |
| Invalid / Malformed / Forged JWT | `401 Unauthorized` | `{ success: false, message: 'Invalid or expired token' }` | Unauthenticated |
| Expired JWT token | `401 Unauthorized` | `{ success: false, message: 'Invalid or expired token' }` | Unauthenticated |
| Post-cutoff legacy token (no `sid`) | `401 Unauthorized` | `{ success: false, message: 'Session identifier required. Please re-authenticate.' }` | Unauthenticated |
| Revoked server-side session | `401 Unauthorized` | `{ success: false, message: 'Session has been revoked or expired. Please log in again.' }` | Unauthenticated |
| Expired database session | `401 Unauthorized` | `{ success: false, message: 'Session has been revoked or expired. Please log in again.' }` | Unauthenticated |
| Locked user account (>= 5 failures) | `403 Forbidden` | `{ success: false, message: 'Account is temporarily locked. Please try again later.' }` | Authenticated but access blocked |
| Insufficient role permissions | `403 Forbidden` | `{ success: false, message: 'Forbidden: Insufficient permissions' }` | Authenticated but unauthorized |
