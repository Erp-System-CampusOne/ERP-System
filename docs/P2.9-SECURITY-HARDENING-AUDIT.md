### Executive Summary

Following the initial rehearsal of Work Package P2.9, a comprehensive security-hardening audit was conducted across the authentication, session management, credential migration, and role authorization implementations.

The audit identified and remediated critical security, abuse-resistance, and data hygiene findings:
1. **Sensitive Data Remediation & In-Memory Dynamic Passwords:** All test passwords are generated cryptographically in memory at runtime (`crypto.randomBytes(16).toString('base64').replace(/[^a-zA-Z0-9]/g, 'a') + '!A1'`) and are never hardcoded, logged, or printed. All test accounts use synthetic non-production identities (`@campus.test`) with guaranteed teardown. Any passwords tested in historical transcripts or preliminary execution logs are formally designated as compromised and must be rotated if ever reused on any live or staging system.
2. **Canonical Role Authority Defect (Remediated):** A logic flaw was identified in `roleService.ts` where a user whose canonical roles in `user_role_assignments` were revoked could fall back to their legacy `User.role` (e.g. `'admin'`), resurrecting revoked privileges. This was hardened so canonical assignments are strictly authoritative.
3. **Legacy Account Brute-Force Bypass (Remediated):** Un-migrated legacy accounts without a canonical `user_credentials` row were previously not tracking failed login attempts before their first successful login. This was hardened by creating/tracking failed attempts in `user_credentials` during legacy verification.
4. **Active Session Invalidation on Security Events (Hardened):** Active sessions are now automatically revoked on account lockout (`revokeAllUserSessions`) and on password changes (`updatePasswordSynchronized`).
5. **Legacy Token Cutoff & Transition Boundary (Hardened):** Strict validation of the `iat` claim was implemented (rejecting missing, non-numeric, or future timestamps) along with a maximum 24-hour transition grace window (`TRANSITION_GRACE_PERIOD_SECONDS`).
6. **Fail-Closed Database Error Handling:** All database lookups in `authenticateJWT` and `authorizeRoles` now explicitly fail closed (`HTTP 500`/`401`), preventing any bypass when database services are interrupted.
7. **Environment Isolation & Refusal Gate:** The test runner strictly locks to local loopback `127.0.0.1` and port `5433`, actively aborting if pointed at Neon or any remote target. Database `search_path` and timezone were reconciled to `public` and `UTC`.

The hardened test runner executed **92 security assertions across 8 suites with 100% success (0 defects)**.

### 2. Detailed Technical Evidence & Code Fixes

#### A. Canonical Role Authority Defect (SEC-02)
- **Vulnerability:** When an administrator revoked a user's canonical role assignment (`is_active = false`), `prisma.userRoleAssignment.findMany` with `isActive: true` returned an empty array (`assignments.length === 0`). The code then executed line 30: `const legacyUser = await prisma.user.findUnique(...)` and returned `[legacyUser.role]`. If `User.role` was originally `'admin'`, the user continued to enjoy administrative access indefinitely.
- **Code Fix in `backend/src/services/roleService.ts`:**
```typescript
  // Check if user has ANY canonical role assignments (active or inactive)
  const totalAssignmentsCount = await prisma.userRoleAssignment.count({
    where: { userId }
  });

  if (totalAssignmentsCount > 0) {
    // Canonical RBAC is strictly authoritative: return ONLY active canonical assignments.
    // Explicitly DO NOT fall back to legacy User.role!
    return assignments.map((a) => a.role.code);
  }

  // Fallback to legacy User.role ONLY for un-migrated accounts with zero canonical assignments
  const legacyUser = await prisma.user.findUnique({
    where: { id: userId },
    select: { role: true }
  });
```

#### B. Legacy Account Brute-Force Defense (SEC-03)
- **Vulnerability:** If an attacker targeted an existing user who had not yet logged in since the P2.9 migration, failed password attempts did not increment any counter because `user_credentials` had not been initialized.
- **Code Fix in `backend/src/services/credentialService.ts`:**
```typescript
  // Fallback to legacy User.password
  const isLegacyMatch = await bcrypt.compare(password, user.password);

  if (!isLegacyMatch) {
    // Initialize or track failed attempts for legacy accounts in user_credentials
    try {
      const legacyCred = await prisma.userCredential.upsert({
        where: {
          userId_credentialType: {
            userId: user.id,
            credentialType: 'password'
          }
        },
        create: {
          userId: user.id,
          credentialType: 'password',
          passwordHash: user.password,
          algorithm: 'bcrypt',
          requiresChange: false,
          failedLoginAttempts: 1,
          lockedUntil: null
        },
        update: {
          failedLoginAttempts: { increment: 1 }
        }
      });

      if (legacyCred.failedLoginAttempts >= MAX_FAILED_ATTEMPTS) {
        const lockedUntil = new Date(now.getTime() + LOCKOUT_DURATION_MS);
        await prisma.userCredential.update({
          where: { id: legacyCred.id },
          data: { lockedUntil }
        });

        await revokeAllUserSessions(user.id, 'account_locked_brute_force');

        return {
          success: false,
          locked: true,
          lockedUntil,
          error: 'Account temporarily locked due to multiple failed login attempts.'
        };
      }
    } catch (err: any) {
      console.warn(`[CredentialService] Failed attempt tracking notice for legacy user ${user.id}`);
    }

    return { success: false, error: 'Invalid credentials' };
  }
```

#### D. Hardened Legacy Token Cutoff & Fail-Closed Validation (SEC-05, SEC-06, SEC-07)
- **Code Fix in `backend/src/middlewares/authMiddleware.ts`:**
```typescript
    // Check 2: Legacy Token Transition Window Validation
    // Missing, malformed, or non-numeric iat is strictly rejected
    if (payload.iat === undefined || payload.iat === null || typeof payload.iat !== 'number' || isNaN(payload.iat)) {
      return res.status(401).json({
        success: false,
        message: 'Legacy token rejected: missing or malformed issued-at (iat) claim'
      });
    }

    const nowSec = Math.floor(Date.now() / 1000);

    // Reject tokens claiming to be issued in the future (allowing max 60s clock skew)
    if (payload.iat > nowSec + 60) {
      return res.status(401).json({
        success: false,
        message: 'Legacy token rejected: issued-at timestamp is in the future'
      });
    }

    // Tokens without 'sid' issued on or after the transition cutoff are strictly rejected
    if (payload.iat >= TRANSITION_CUTOFF_TIMESTAMP) {
      return res.status(401).json({
        success: false,
        message: 'Legacy token issued after migration cutoff is invalid. Re-authentication required.'
      });
    }

    // Legacy tokens cannot bypass cutoff indefinitely: reject if grace window has elapsed
    if (nowSec > TRANSITION_CUTOFF_TIMESTAMP + TRANSITION_GRACE_PERIOD_SECONDS) {
      return res.status(401).json({
        success: false,
        message: 'Legacy token transition window has expired. Please log in again.'
      });
    }
```

### 4. Database Identity Boundary & Isolation Verification

- **Mechanism:** `identityContext.executeWithIdentity(userId, callback)` uses Prisma interactive transactions to execute:
  `SET LOCAL app.current_user_id = $userId;` (via `set_config('app.current_user_id', userId, true)`).
- **Scope Property:** Because `is_local = true` is supplied, PostgreSQL automatically scopes this setting strictly to the current transaction. When the transaction commits or rolls back, the GUC setting is cleared before the pooled connection is returned to the pool.
- **Audited Boundary:** This mechanism is verified to prevent connection-pool leakage across concurrent requests (asserted in Suite 7 via 10 parallel transactions).
- **Security Boundary Distinction:** As confirmed in the audit, `app.current_user_id` serves as a transaction-scoping and consistency guardrail. It **does not** constitute independent cryptographic proof of caller identity against an attacker capable of executing arbitrary SQL as the application database role.
- **Operational Guardrail:** Production grade-correction procedures remain **STRICTLY BLOCKED** until trusted identity binding, stored procedure assertions, and audit triggers are implemented and verified in P2.10.

### 6. Remaining Risks & Unresolved Institutional Decisions

While P2.9 technical hardening in the disposable environment is complete with 92/92 passing assertions, the following risks and policy decisions remain open prior to any production consideration:

1. **Self-Service Account Recovery vs. Administrative Unlock:**
   - *Current Implementation:* Accounts unlock automatically after 15 minutes (`LOCKOUT_DURATION_MS = 15 * 60 * 1000`).
   - *Residual Risk:* A persistent attacker could script login attempts every 15 minutes to cause continuous intermittent denial of service against a known user email.
   - *Decision Needed:* Does the institution require an administrative unlock endpoint (`/api/admin/users/:id/unlock`), an email-based password reset unlock flow, or IP-based rate limiting (via WAF or Redis) in addition to account-level lockout?
2. **Transition Grace Period Policy for Legacy Mobile / Embedded Clients:**
   - *Current Implementation:* Legacy tokens without `sid` are accepted up to `TRANSITION_CUTOFF_TIMESTAMP + 24 hours` (`TRANSITION_GRACE_PERIOD_SECONDS = 86400`).
   - *Residual Risk:* If any third-party integration or active client has a long-lived token issued prior to deployment that needs longer than 24 hours to re-authenticate, it will receive `HTTP 401`.
   - *Decision Needed:* Confirm whether 24 hours is acceptable to campus stakeholders or if an explicit administrative grace exception list is needed.
3. **Application Database Role Privileges (PostgreSQL DDL/DML Guardrails):**
   - *Current Implementation:* `identityContext` scopes `SET LOCAL app.current_user_id` inside Prisma transactions.
   - *Residual Risk:* As proven in Section 4, `app.current_user_id` does not stop direct SQL modifications if application credentials are leaked or if stored procedures do not enforce role checks.
   - *Next Step (P2.10):* P2.10 will implement trusted stored procedures, explicit `SECURITY DEFINER` constraints, and audit trigger validation for grade-correction workflows.
